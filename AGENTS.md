## What this is

> **New to the repo? Start with [`TOUR.md`](TOUR.md)** — a high-level map of what's here, why there are three runtimes, and where to read next. This file (`AGENTS.md`) is the working reference: commands, environment, conventions.

**Helix** is the AZX App Platform: secure hosting for vibe-coded AI apps. The whole design rests on one stance — **every hosted app is untrusted code** — and contains the blast radius per app rather than trying to verify app code. Read `docs/platform-architecture.md` (the _what & why_) and `docs/platform-project-plan.md` (the _with what & in what order_) before making non-trivial decisions; section references like "§4.2" or "project plan §6" throughout the code point into these. `docs/adr/` records the significant architecture decisions one-per-file (Context → Decision → Consequences), and is the canonical record of _why_ — where an ADR and older prose disagree, the ADR wins. `docs/features/` holds up-to-date per-feature docs (what & how, today), and `docs/design/app-data-storage.md` is the app-data design. Open follow-up work distilled from the ADRs lives in [`TODO.md`](TODO.md).

**Current status: deployed on Azure (M5).** The three planes run in production on Container Apps against real Entra OIDC, wildcard TLS, and a live Key Vault — `infra/azure` (Bicep) is the source of truth for the topology, and `infra/azure/README.md` is the operational reference. The outstanding M5 residual is a real pilot app end to end. **Everything still runs fully locally** — `apps/dev-idp` stands in for Entra, the dev AES-GCM envelope for Key Vault, Azurite for Blob — so treat "local" below as the development path, not the only deployment. Where a doc says something is "local only", check it against this line.

Feature-wise the platform is at **M4.5 — Egress & Connections.** Everything M2/M3/M4 had (portal registry/deploy API, `helix` CLI, edge serving on `<slug>.local.helix.azxlabs.io` with a LISTEN/NOTIFY registry projection, Blob streaming over undici (managed-identity bearer in prod, hand-signed SharedKey dev/Azurite-only — ADR-0027/issue #15), §4.4 CSP, 404/410 semantics, the `/_api/*` LLM + app-data gateway) **plus** the **`helix-egress`** mechanism plane (`apps/egress`, `pnpm dev:egress`, :8081) running the fetch-proxy and secret-backed connections — a **third deployable container from day one** (architecture §3 now reasons "why three, not two"). See below for the auth half, the gateway half, and the egress half.

The §4.2/Appendix A auth flow runs against **real Entra in the deployed platform** and against a **local OIDC issuer** in development (`apps/dev-idp` — an oidc-provider wrapper with fixture users alice/bob/mallory; `pnpm dev:idp`, :3002; never deployed). The issuer is one env-level swap, which was the point of the design — the flow itself is identical either way: central callback on `auth.<base>`, one-time handoff token (signed, 30 s, single-use, audience-bound; burned by an atomic UPDATE on the portal-migrated `sessions` table), `__Host-session` cookies (the edge terminates TLS in dev via mkcert — certs in gitignored `.devcontainer/certs/`, generated by post-create), a session gate on app hosts (navigations 302 to login, fetches 401), group visibility re-checked per request, silent refresh via `prompt=none`, `/_api/me`, and Origin-checked logout — see `apps/edge/README.md`. **`password` visibility** (shared-password apps for external demos) also lands locally: the portal mints/stores an xkcd-style passphrase (scrypt hash projected to the edge, AES-GCM ciphertext kept portal-side for re-display) via `/api/v1/apps/:slug/access/password`, and the edge serves a same-origin `/_auth/login` challenge (Origin-checked, throttled, async-scrypt verify) that mints a pseudonymous (`pw_<random>`) session — no OIDC, no handoff (`apps/edge/src/auth/routes/passwordLogin.ts`, see `docs/features/authentication.md`). (Issue #13 is closed — ADR-0011: the login throttle and the anon per-IP limiter now share one **PG-backed counter** (`PgCounterStore`, `rate_counters`), so limits hold across the horizontally-scaled fleet instead of N×-per-replica; the atomic upsert makes the throttle reserve-first, closing the check-then-increment TOCTOU; scrypt is at OWASP's `N=2^17`; and `EDGE_TRUST_PROXY` is verified and set in the deployments, so `${req.ip}:${appId}` keys on the real client rather than the ingress hop.) The adversarial suite is `apps/edge/src/auth/adversarial.test.ts` plus integration twins — anything touching that path changes tests in lockstep (project plan §6). Portal mutating routes accept **bearer JWTs** verified statelessly over the issuer's JWKS (`PORTAL_DEV_TOKEN` is demoted to one verifier in the chain for CI/scripts and refused in production); the CLI has `helix login` (OIDC device flow), `logout`, and `whoami` with an XDG token cache (`HELIX_TOKEN` still short-circuits).

The **`/_api/*` gateway** (architecture §6.1) has landed locally: `POST /_api/llm/chat` (LLM proxy — session-gated, Origin/CSRF-checked, manifest model allowlist + daily token budget, hand-rolled Anthropic SSE over undici through an `LlmProvider` seam so the app never sees the key, every call metered), and `/_api/data/*` app-data in three scopes — per-user (RLS-partitioned via `SET LOCAL` GUCs from the verified session), write-only `collections` (no app-facing read; owner drains via the portal export API), and app-`shared` keys. Both gate off one `Caller` seam (`apps/edge/src/auth/gate.ts`) that yields an anonymous caller on `public` apps. The real containment is a Postgres **role split**: `helix_edge` reads the registry, appends to `gateway_calls`, has INSERT-only on `app_collection_items`, and RLS-partitioned `app_data` — it cannot enumerate collections or write the registry (`role-split.integration.test.ts`). Both the real Entra registration and the Azure deploy have since landed — see the status line above.

The **fetch-proxy + secret-backed connections** (M4.5) split the policy and mechanism planes across two services. `/_api/fetch/<url>` on the **edge** authorizes (gate, Origin/CSRF, the manifest proxy-origin allowlist `capabilities.fetch.origins`, a per-app `requestsPerDay` budget), mints a short-lived signed **attested instruction** (`jose`/HKDF off `HELIX_INSTRUCTION_SECRET`, the same primitives as the handoff token), and forwards the call over the `EgressProvider` seam to **`helix-egress`** — which verifies the instruction, resolves the named **connection secret** to plaintext (`PgSecretResolver` under a dedicated `helix_egress` role), injects the credential server-side, applies SSRF controls (`apps/egress/src/ssrf.ts`: block private/loopback/IMDS, pin the validated IP against rebind, no redirect-follow, a request-header safelist and a response-header **blocklist**), and streams the upstream response back. (Per ADR-0005 `www-authenticate` is intentionally left off the blocklist as a server challenge, not a reflection; the injected-credential reflection strip (issue #7) and a **framing-independent body-size cap** (issue #8 — a byte counter enforcing `maxBodyBytes` on both hops in both directions via `@azx-pbc/shared` `capBody`, so chunked / CL-absent / lying-`content-length` bodies are all counted; request overflow → 413, response overflow truncates) have both landed.) Secrets are sealed by the **`SecretStore`** seam (`packages/secret-store` — dev AES-GCM envelope under a post-create-generated KEK; **prod Key Vault is wired**, `material` is a version-pinned `kv:<name>/<version>` reference, hand-rolled data-plane REST so the package stays zero-dep, with a documented timeout/retry budget, a version-pinned plaintext cache, and a `release()`/compare-and-swap rollback so a failed or concurrent seal→write can't strand a live vault entry — ADR-0006 amendment; verified against a live Key Vault in the deployment), managed write-only via the portal (`apps/portal/src/routes/secrets.ts`, app-scoped + admin-global with grants), and **never readable by `helix_edge`** — the policy edge has no grant on `app_secrets` at all, so an edge RCE can't dump a single key (`role-split.integration.test.ts`, `apps/egress/src/adversarial.test.ts`). The manifest binding (a proxied origin → a connection) rides the existing approval write-gate. The **transparent fetch shim** is now wired end to end: opt-in via `capabilities.fetch.shim`, served at `/_helix/fetch-shim.js` and injected into the `<head>` of `text/html` responses at serve time (`apps/edge/src/serving/shim.ts`), monkeypatching `fetch` + `XMLHttpRequest` so granted origins route through `/_api/fetch/<url>` unedited; the global-admin **Secrets SPA page** (`/admin/secrets`) is real and wired too.

**Pulled forward from v1: the portal SPA** (`apps/portal-web` — Vite + React 19 + **Mantine** + TanStack Query + React Router; the one package on `moduleResolution: bundler` instead of nodenext). Real and wired to the live API: app list/detail, version history with promote/rollback, create app, zip-upload deploy (renders the CSP lint warnings), archive/unarchive, a real capability-manifest editor (`GET`/`PUT /api/v1/apps/:slug/manifest`), and browser sign-in (code+PKCE via a third public dev-idp client `azx-portal-web`; `clientBasedCORS` opens the token endpoint to it; the token is held per-tab in sessionStorage and now gates every page — a `RequireAuth` gate wraps the SPA and `RequireAdmin` gates `/admin/*` on the `isAdmin` flag from `/me`). The usage/metering dashboards and the gateway audit log are real and wired (`/api/v1/apps/:slug/usage`, `/api/v1/gateway/usage`, `/api/v1/gateway/audit` over `gateway_calls`), as are the **capability-approvals queue** (`/api/v1/approvals`), the **CSP violations** screen (`/api/v1/csp/violations` → one-click origin grant), and the **global secrets** admin page (`/api/v1/secrets`). Every portal screen is now real; the only remaining `PreviewBadge` marks **per-app RBAC** (owner/editor/viewer roles, a v1 feature) in the Settings tab — not mock data, just a not-yet-built sub-feature, never silently faked. Note the v0 authorization posture behind that badge is [ADR-0007](docs/adr/0007-portal-authz-v0.md). The BOLA half is **closed**: an `ownsApp` owner-or-admin preHandler (`apps/portal/src/plugins/auth.ts`, fail-closed on a null `ownerId`) guards every app-scoped mutating route plus the credential-returning password read, with an adversarial sweep in `ownership.test.ts` (issue #9). What remains is per-app **RBAC** (owner/editor/viewer) — reads are still authenticated-only, and the SPA still renders mutate controls for non-owned apps, with the server 403 as the boundary. The portal serves `portal-web/dist` statically when present (deep links fall back to index.html; `/api` + `/health` stay JSON) and falls back to the old stopgap dashboard when not. In dev, `pnpm dev:web` (:5173) proxies `/api` to :3001 — no CORS anywhere. Because that `dist/` is baked into the portal image, the SPA's **only build-time config is the portal origin**: deployment topology (`appPublicBase`, the opt-in `devApiBase`, `platformMonthlyUsdCap`) comes from the public `GET /api/v1/config` at runtime (`apps/portal/src/deployment.ts` → `apps/portal-web/src/lib/deployment.ts`), and every app the API returns carries a control-plane-computed `url`. Never reintroduce a `VITE_*` domain var or derive the apps host from `window.location` — see `docs/features/portal-web.md`.

## Environment

Work inside the **dev container** (VS Code: _Reopen in Container_). It provides Node 24, pnpm, and the `db` (Postgres 18) + `azurite` (Blob) services, with `DATABASE_URL`, `AZURE_STORAGE_CONNECTION_STRING`, and the M3 auth env (`EDGE_OIDC_*`, `EDGE_AUTH_SECRET`, `EDGE_TLS_*`, `PORTAL_OIDC_*`) already set. The local IdP is **not** a compose service — it runs in the workspace container (`pnpm dev:idp`) so its issuer URL (`http://localhost:3002`) reads identically from the host browser and from in-container back-channels. mkcert TLS certs for `*.local.helix.azxlabs.io` are generated by post-create into `.devcontainer/certs/` (gitignored). `pnpm install` runs on create. Node 24 LTS is required (`engines.node >=24`).

## Architecture

The system is **three deployable containers plus managed storage**, split along the trust boundary (architecture §3):

- **`apps/edge` — helix-edge, the data/policy plane.** Stateless. Terminates all untrusted app-user traffic (`*.local.helix.azxlabs.io` in dev, `*.azx.helix.azxlabs.io` in prod): host routing, session auth + OIDC handoff, CSP injection, asset serving from Blob, and the `/_api/*` gateway — the LLM proxy, app-data (user/collection/shared), and the **fetch-proxy policy** (authz/quota/audit, then a signed instruction to egress). Runs as the least-privilege `helix_edge` role: a read-only registry projection, INSERT-only metering/collections, RLS-partitioned app-data — **no registry-write and no secret-read** access.
- **`apps/portal` — helix-portal, the control plane.** Privileged: portal UI/API, deploy endpoint, registry writes, capability approvals, secret writes. Not routable from app subdomains. Owns the Postgres schema and all migrations (Prisma 7, pg driver adapter); the edge only reads a cached projection.
- **`apps/egress` — helix-egress, the mechanism plane.** The only component holding plaintext connection secrets or a route to the public internet. Internal-only (`POST /proxy`, never app-user-facing): verifies the edge's attested instruction, resolves+injects the secret under the `helix_egress` role, enforces SSRF controls, and streams the outbound call back. Its own network egress zone in prod; built as its own container from day one rather than extracted later.
- **`packages/secret-store` — `@azx-pbc/secret-store`.** The `seal`/`open`/`destroy` custody seam shared by the portal (write) and egress (read): dev AES-GCM envelope / prod Key Vault behind one interface. **Zero runtime dependencies** — it is consumed by the mechanism plane, so the Key Vault impl is hand-rolled data-plane REST over global `fetch` with the credential injected as a one-function `GetVaultToken` seam (egress hand-rolls the managed-identity call; the portal injects `DefaultAzureCredential`). Keep it dependency-free.
- **`packages/shared` — `@azx-pbc/shared`.** zod schemas validated at every boundary (visibility, app, version, manifest, health), with inferred types exported alongside. Re-exported from `src/index.ts`; consumed via `workspace:*`. Note `@azx-pbc/shared` exports `./src/index.ts` directly (no build step).

`packages/cli` — `@azx-pbc/helix-cli`, the `helix` CLI — landed in M1 (zips a build dir or a prebuilt bundle and drives the deploy API) and is **published to public npm** (`npm i -g @azx-pbc/helix-cli`) from `.github/workflows/release-cli.yml` on a `cli-v*` tag, via trusted publishing (OIDC, no `NPM_TOKEN`) with provenance — ADR-0032. It is the only non-`private` package in the repo and the only one that emits JS. And `apps/portal-web` (the React SPA) is real and wired (see above). `packages/deploy-skill` is the **agent skill bundle** — a templated `SKILL.md` teaching an agent how to build and deploy a Helix app, rendered for this deployment and handed out by the portal SPA's **How to develop** modal (`docs/features/onboarding.md`). `infra/` appears in the target layout (project plan §2) but lands in a later milestone.

### The edge is the trusted path

**Hard rule: `apps/edge` is dependency-minimal.** Every npm package there is code inside the trusted path, so adding a runtime dependency requires justification at review time (project plan §6). No ORM in the edge — hand-written SQL. Never block the event loop; pipe streams, never buffer LLM responses.

### App boot pattern

Both apps follow the same shape: `src/app.ts` exports `buildApp(): FastifyInstance` (pure, testable, no listen), and `src/server.ts` imports it and calls `app.listen()`. Tests build the app and inject requests rather than binding a port. The `/health` endpoint validates its own response through `HealthStatusSchema` so the contract is identical across services. That contract is a three-state roll-up (`ok`/`degraded`/`error`) plus an optional generic `checks[]` array, not a liveness boolean — the edge reports its registry projection's freshness there (ADR-0025). **It always answers HTTP 200**, in every state: the body carries the degradation, because a non-200 would let a liveness probe restart a replica that is serving correctly from a stale copy. Portal and egress report liveness only (no `checks`).

## Conventions

- **TypeScript everywhere, ESM, Node 24.** Strict `tsconfig.base.json` (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `isolatedModules`), extended per package. Because of `verbatimModuleSyntax`, type-only imports must be written as `import type` / `import { type X }`. ESM import specifiers use `.js` extensions even for `.ts` sources (`nodenext`).
- **Versions via the pnpm catalog** in `pnpm-workspace.yaml` — packages reference `catalog:` instead of pinning; bump in one place.
- **zod at every boundary** (`@azx-pbc/shared`); inferred types travel with the schemas.
- **Tests** are colocated `*.test.ts` under each package's `src/`; Vitest runs them in the `node` environment (single project for now — a jsdom project splits off when the React SPA lands).
- **Anything touching M3 auth code gets adversarial tests with it, not after** (project plan §6). The OIDC handoff is the most security-sensitive code in the platform and gets a dedicated review pass.
