## What this is

> **New to the repo? Start with [`TOUR.md`](TOUR.md)** — a high-level map of what's here, why there are three runtimes, and where to read next. This file (`AGENTS.md`) is the working reference: commands, environment, conventions.

**Helix** is the AZX App Platform: secure hosting for vibe-coded AI apps. The whole design rests on one stance — **every hosted app is untrusted code** — and contains the blast radius per app rather than trying to verify app code. Read `docs/platform-architecture.md` (the _what & why_) and `docs/platform-project-plan.md` (the _with what & in what order_) before making non-trivial decisions; section references like "§4.2" or "project plan §6" throughout the code point into these. `docs/adr/` records the significant architecture decisions one-per-file (Context → Decision → Consequences), and is the canonical record of _why_ — where an ADR and older prose disagree, the ADR wins. `docs/features/` holds up-to-date per-feature docs (what & how, today), and `docs/design/app-data-storage.md` is the app-data design. Open follow-up work distilled from the ADRs lives in [`TODO.md`](TODO.md).

**Current status: M4.5 (local) — Egress & Connections.** Everything M2/M3/M4 had (portal registry/deploy API, `azx` CLI, edge serving on `<slug>.localtest.me` with a LISTEN/NOTIFY registry projection, Blob streaming over undici (managed-identity bearer in prod, hand-signed SharedKey dev/Azurite-only — ADR-0027/issue #15), §4.4 CSP, 404/410 semantics, the `/_api/*` LLM + app-data gateway) **plus** the **`azx-egress`** mechanism plane (`apps/egress`, `pnpm dev:egress`, :8081) running the fetch-proxy and secret-backed connections — a **third deployable container from day one** (architecture §3 now reasons "why three, not two"). See below for the auth half, the gateway half, and the egress half.

The §4.2/Appendix A auth flow runs against a **local OIDC issuer** (`apps/dev-idp` — an oidc-provider wrapper with fixture users alice/bob/mallory; `pnpm dev:idp`, :3002): central callback on `auth.<base>`, one-time handoff token (signed, 30 s, single-use, audience-bound; burned by an atomic UPDATE on the portal-migrated `sessions` table), `__Host-session` cookies (the edge terminates TLS in dev via mkcert — certs in gitignored `.devcontainer/certs/`, generated by post-create), a session gate on app hosts (navigations 302 to login, fetches 401), group visibility re-checked per request, silent refresh via `prompt=none`, `/_api/me`, and Origin-checked logout — see `apps/edge/README.md`. **`password` visibility** (shared-password apps for external demos) also lands locally: the portal mints/stores an xkcd-style passphrase (scrypt hash projected to the edge, AES-GCM ciphertext kept portal-side for re-display) via `/api/v1/apps/:slug/access/password`, and the edge serves a same-origin `/_auth/login` challenge (Origin-checked, throttled, async-scrypt verify) that mints a pseudonymous (`pw_<random>`) session — no OIDC, no handoff (`apps/edge/src/auth/routes/passwordLogin.ts`, see `docs/features/authentication.md`). (Caveats per ADR-0004/0011: the login throttle is in-memory single-replica and non-atomic — weakened under the shipped `maxReplicas>1` — and scrypt cost is below OWASP; tracked as issue #13.) The adversarial suite is `apps/edge/src/auth/adversarial.test.ts` plus integration twins — anything touching that path changes tests in lockstep (project plan §6). Portal mutating routes accept **bearer JWTs** verified statelessly over the issuer's JWKS (`PORTAL_DEV_TOKEN` is demoted to one verifier in the chain for CI/scripts and refused in production); the CLI has `azx login` (OIDC device flow), `logout`, and `whoami` with an XDG token cache (`AZX_TOKEN` still short-circuits).

The **`/_api/*` gateway** (architecture §6.1) has landed locally: `POST /_api/llm/chat` (LLM proxy — session-gated, Origin/CSRF-checked, manifest model allowlist + daily token budget, hand-rolled Anthropic SSE over undici through an `LlmProvider` seam so the app never sees the key, every call metered), and `/_api/data/*` app-data in three scopes — per-user (RLS-partitioned via `SET LOCAL` GUCs from the verified session), write-only `collections` (no app-facing read; owner drains via the portal export API), and app-`shared` keys. Both gate off one `Caller` seam (`apps/edge/src/auth/gate.ts`) that yields an anonymous caller on `public` apps. The real containment is a Postgres **role split**: `helix_edge` reads the registry, appends to `gateway_calls`, has INSERT-only on `app_collection_items`, and RLS-partitioned `app_data` — it cannot enumerate collections or write the registry (`role-split.integration.test.ts`). Remaining: a real Entra app registration (M3 tail, config-only) and the Azure deploy (M5).

The **fetch-proxy + secret-backed connections** (M4.5) split the policy and mechanism planes across two services. `/_api/fetch/<url>` on the **edge** authorizes (gate, Origin/CSRF, the manifest proxy-origin allowlist `capabilities.fetch.origins`, a per-app `requestsPerDay` budget), mints a short-lived signed **attested instruction** (`jose`/HKDF off `HELIX_INSTRUCTION_SECRET`, the same primitives as the handoff token), and forwards the call over the `EgressProvider` seam to **`azx-egress`** — which verifies the instruction, resolves the named **connection secret** to plaintext (`PgSecretResolver` under a dedicated `helix_egress` role), injects the credential server-side, applies SSRF controls (`apps/egress/src/ssrf.ts`: block private/loopback/IMDS, pin the validated IP against rebind, no redirect-follow, a request-header safelist and a response-header **blocklist**), and streams the upstream response back. (Per ADR-0005 the response blocklist has gaps — it omits `authorization`/`www-authenticate`, and body caps read only `content-length` — tracked as issues #7/#8; treat "both ways" claims in older docs as aspirational.) Secrets are sealed by the **`SecretStore`** seam (`packages/secret-store` — dev AES-GCM envelope under a post-create-generated KEK; prod Key Vault, wired in M5), managed write-only via the portal (`apps/portal/src/routes/secrets.ts`, app-scoped + admin-global with grants), and **never readable by `helix_edge`** — the policy edge has no grant on `app_secrets` at all, so an edge RCE can't dump a single key (`role-split.integration.test.ts`, `apps/egress/src/adversarial.test.ts`). The manifest binding (a proxied origin → a connection) rides the existing approval write-gate. The **transparent fetch shim** is now wired end to end: opt-in via `capabilities.fetch.shim`, served at `/_helix/fetch-shim.js` and injected into the `<head>` of `text/html` responses at serve time (`apps/edge/src/serving/shim.ts`), monkeypatching `fetch` + `XMLHttpRequest` so granted origins route through `/_api/fetch/<url>` unedited; the global-admin **Secrets SPA page** (`/admin/secrets`) is real and wired too. _Deferred to M5:_ the prod Key Vault `SecretStore` impl (the dev AES-GCM envelope works today).

**Pulled forward from v1: the portal SPA** (`apps/portal-web` — Vite + React 19 + **Mantine** + TanStack Query + React Router; the one package on `moduleResolution: bundler` instead of nodenext). Real and wired to the live API: app list/detail, version history with promote/rollback, create app, zip-upload deploy (renders the CSP lint warnings), archive/unarchive, a real capability-manifest editor (`GET`/`PUT /api/v1/apps/:slug/manifest`), and browser sign-in (code+PKCE via a third public dev-idp client `azx-portal-web`; `clientBasedCORS` opens the token endpoint to it; the token is held per-tab in sessionStorage and now gates every page — a `RequireAuth` gate wraps the SPA and `RequireAdmin` gates `/admin/*` on the `isAdmin` flag from `/me`). The usage/metering dashboards and the gateway audit log are real and wired (`/api/v1/apps/:slug/usage`, `/api/v1/gateway/usage`, `/api/v1/gateway/audit` over `gateway_calls`), as are the **capability-approvals queue** (`/api/v1/approvals`), the **CSP violations** screen (`/api/v1/csp/violations` → one-click origin grant), and the **global secrets** admin page (`/api/v1/secrets`). Every portal screen is now real; the only remaining `PreviewBadge` marks **per-app RBAC** (owner/editor/viewer roles, a v1 feature) in the Settings tab — not mock data, just a not-yet-built sub-feature, never silently faked. Note the v0 authorization posture behind that badge is [ADR-0007](docs/adr/0007-portal-authz-v0.md): authenticated == authorized — any authenticated principal can mutate any app and manage any app's secrets. That is a deliberate v0 choice, but the app-scoped secrets/mutating routes doing **no ownership check** is a live BOLA to gate before M5 (issue #9), not a benign cosmetic gap. The portal serves `portal-web/dist` statically when present (deep links fall back to index.html; `/api` + `/health` stay JSON) and falls back to the old stopgap dashboard when not. In dev, `pnpm dev:web` (:5173) proxies `/api` to :3001 — no CORS anywhere.

## Environment

Work inside the **dev container** (VS Code: _Reopen in Container_). It provides Node 24, pnpm, and the `db` (Postgres 18) + `azurite` (Blob) services, with `DATABASE_URL`, `AZURE_STORAGE_CONNECTION_STRING`, and the M3 auth env (`EDGE_OIDC_*`, `EDGE_AUTH_SECRET`, `EDGE_TLS_*`, `PORTAL_OIDC_*`) already set. The local IdP is **not** a compose service — it runs in the workspace container (`pnpm dev:idp`) so its issuer URL (`http://localhost:3002`) reads identically from the host browser and from in-container back-channels. mkcert TLS certs for `*.localtest.me` are generated by post-create into `.devcontainer/certs/` (gitignored). `pnpm install` runs on create. Node 24 LTS is required (`engines.node >=24`).

## Architecture

The system is **three deployable containers plus managed storage**, split along the trust boundary (architecture §3):

- **`apps/edge` — azx-edge, the data/policy plane.** Stateless. Terminates all untrusted app-user traffic (`*.localtest.me` in dev, `*.azx-labs.com` in prod): host routing, session auth + OIDC handoff, CSP injection, asset serving from Blob, and the `/_api/*` gateway — the LLM proxy, app-data (user/collection/shared), and the **fetch-proxy policy** (authz/quota/audit, then a signed instruction to egress). Runs as the least-privilege `helix_edge` role: a read-only registry projection, INSERT-only metering/collections, RLS-partitioned app-data — **no registry-write and no secret-read** access.
- **`apps/portal` — azx-portal, the control plane.** Privileged: portal UI/API, deploy endpoint, registry writes, capability approvals, secret writes. Not routable from app subdomains. Owns the Postgres schema and all migrations (Prisma 7, pg driver adapter); the edge only reads a cached projection.
- **`apps/egress` — azx-egress, the mechanism plane.** The only component holding plaintext connection secrets or a route to the public internet. Internal-only (`POST /proxy`, never app-user-facing): verifies the edge's attested instruction, resolves+injects the secret under the `helix_egress` role, enforces SSRF controls, and streams the outbound call back. Its own network egress zone in prod; built as its own container from day one rather than extracted later.
- **`packages/secret-store` — `@azx-pbc/secret-store`.** The `seal`/`open`/`destroy` custody seam shared by the portal (write) and egress (read): dev AES-GCM envelope / prod Key Vault behind one interface.
- **`packages/shared` — `@azx-pbc/shared`.** zod schemas validated at every boundary (visibility, app, version, manifest, health), with inferred types exported alongside. Re-exported from `src/index.ts`; consumed via `workspace:*`. Note `@azx-pbc/shared` exports `./src/index.ts` directly (no build step).

`packages/cli` — `@azx-pbc/cli`, the `azx` CLI — landed in M1 (zips a build dir or a prebuilt bundle and drives the deploy API), and `apps/portal-web` (the React SPA) is real and wired (see above). `packages/deploy-skill` and `infra/` appear in the target layout (project plan §2) but land in later milestones.

### The edge is the trusted path

**Hard rule: `apps/edge` is dependency-minimal.** Every npm package there is code inside the trusted path, so adding a runtime dependency requires justification at review time (project plan §6). No ORM in the edge — hand-written SQL. Never block the event loop; pipe streams, never buffer LLM responses.

### App boot pattern

Both apps follow the same shape: `src/app.ts` exports `buildApp(): FastifyInstance` (pure, testable, no listen), and `src/server.ts` imports it and calls `app.listen()`. Tests build the app and inject requests rather than binding a port. The `/health` endpoint validates its own response through `HealthStatusSchema` so the contract is identical across services.

## Conventions

- **TypeScript everywhere, ESM, Node 24.** Strict `tsconfig.base.json` (`strict`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `isolatedModules`), extended per package. Because of `verbatimModuleSyntax`, type-only imports must be written as `import type` / `import { type X }`. ESM import specifiers use `.js` extensions even for `.ts` sources (`nodenext`).
- **Versions via the pnpm catalog** in `pnpm-workspace.yaml` — packages reference `catalog:` instead of pinning; bump in one place.
- **zod at every boundary** (`@azx-pbc/shared`); inferred types travel with the schemas.
- **Tests** are colocated `*.test.ts` under each package's `src/`; Vitest runs them in the `node` environment (single project for now — a jsdom project splits off when the React SPA lands).
- **Anything touching M3 auth code gets adversarial tests with it, not after** (project plan §6). The OIDC handoff is the most security-sensitive code in the platform and gets a dedicated review pass.
