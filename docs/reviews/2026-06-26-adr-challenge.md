# ADR Adversarial Challenge — multi-model panel

**Date:** 2026-06-26
**Method:** Each of the 13 ADRs in `docs/adr/` was challenged by a 5-model panel (GLM 5.1, DeepSeek v4 Pro, Kimi k2.7, Qwen 3.7, MiniMax m3) under read-only agents, each prompted to make the strongest *evidence-based* case to break the decision (UPHOLD / WEAKEN / OVERTURN), grounded in the actual code and best practice. 65 reviews total. Brave grounding on the foundational claims; two contested factual claims verified directly against source.

> Verdict scale — **UPHOLD:** sound as written. **WEAKEN:** the decision stands but the ADR overstates delivery or omits a material caveat/precondition. **OVERTURN:** wrong, premature, or a materially better alternative exists.

## Headline

**No decision was overturned.** Every ADR came back **WEAKEN** (one model rated 0011 OVERTURN). The pattern is uniform and important: **the decisions are directionally right, but the ADR *text* repeatedly overstates what the code delivers and omits preconditions that are load-bearing for the claim.** The challenge surfaced concrete, mostly-cheap amendments, plus two factual corrections to ADRs I wrote.

## Two verified corrections

- **ADR-0013 was partly wrong.** `PgSecretResolver.resolve` (`apps/egress/src/secrets.ts:48-92`) **does** scope `fetch` connection secrets by `appId` and re-checks `app_secret_grants` for `global` secrets. Per-app authorization is *already present* for connection secrets. The real residual is narrower: (a) the **`llm`/platform** path resolves a platform secret **by name only**; (b) **no path binds the instruction's `origin` (or method/path) to the connection**; and (c) because the instruction key is a **shared symmetric secret, the `appId` claim is forgeable** — that, not missing authz, is the cross-app vector.
- **ADR-0011's single-replica premise is already false.** `infra/azure/modules/containerapp.bicep:43` sets `maxReplicas = 3` (default) for the edge; `apps/edge/src/server.ts:188` schedules only `anonRateLimiter.sweep()` — `loginThrottle.sweep()` is never wired. The "v0 single-replica" scope ships falsified into the M5 pilot.

## Cross-cutting meta-findings (appeared across multiple ADRs)

1. **ADRs state target-state as present-tense.** 0001 ("no secret"), 0002 ("each runtime connects as a distinct role"), 0005 ("safelist both ways"), 0011 ("single-replica") all describe the intent, not the running code. Every "Status: Accepted" ADR should separate *decided* from *delivered*, and move the gap into Consequences/Open-questions rather than only the review notes.
2. **The symmetric-HKDF pattern recurs** — handoff token, egress instruction, and the planned signed-identity header all use a shared symmetric secret. The prior review flagged shared-symmetric as an anti-pattern for *egress*; the panel notes it's becoming a *family* pattern. Per-app-derived (and eventually asymmetric) keys should be the standard, decided once.
3. **"v0 / defer to v1" markers have no forcing function.** 0007, 0011, 0012 all defer a real control with a prose "before M5 / before multi-tenant" that nothing enforces — and M5 *is* the pilot. Each needs a concrete gate (a CI check or an M5 exit-criterion test), not a milestone label.
4. **Unenforced rules** — the dependency-minimal rule (0003) and the co-deploy split (0012) are both review-discipline-only; the panel wants mechanical gates.

## What did NOT survive challenge (challenges the panel refuted)

- "IP-literal dial breaks TLS" (0005) — refuted: `servername: target.hostname` preserves SNI/cert validation.
- "Egress doesn't authorize connection secrets" (0013) — refuted by code: the `fetch` path is app-scoped + grant-checked.
- "Bespoke handoff token is wrong" (0004) — refuted: `__Host-` cookies can't be set cross-subdomain, so a cross-origin carrier is architecturally required; the handoff is the right primitive.
- "Three runtimes is over-decomposition" (0001) — not sustained: the split is along a *trust boundary* (a legitimate reason), not arbitrary code-size; egress earns its split.
